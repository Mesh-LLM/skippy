# Serving configuration

Serving configuration defines how Skippy loads a model, allocates resources,
schedules requests, exposes APIs, and records reusable state. Every supported
operator control is available through `skippy serve --help`.

Use CLI options for temporary overrides and experiments. Use environment
variables for process-level deployment settings. Use `--settings serve.toml`
for a complete, reviewable serving configuration.

## Create a settings file

```toml
version = 1

[model]
model = "Qwen3-0.6B-Q4_K_M"
mmap = true

[execution]
n_gpu_layers = -1
threads = 4
batch_size = 512

[kv]
ctx_size = 8192
kv_cache_type_k = "f16"
kv_cache_type_v = "f16"

[cache]
prefix_cache = "auto"
kv_cache_disk = "off"

[scheduling]
generation_concurrency = 2
continuous_batching = true

[api]
bind_addr = "127.0.0.1:9337"
default_max_tokens = 2048
```

Run with an override and inspect the resolved launch:

```console
skippy serve --settings serve.toml --temperature 0.2
skippy serve --settings serve.toml --print-effective-config
```

## Serve multiple local models

Save this as `serving.toml` to serve two Hugging Face GGUFs on one listener.

```toml
version = 1

[[models]]
model = "Qwen/Qwen3-0.6B-GGUF:Q8_0"

[[models]]
model = "Qwen/Qwen3-1.7B-GGUF:Q8_0"
```

```console
skippy serve --settings serving.toml
```

Both `[model].model` and `[[models]].model` accept the same inputs as
`skippy serve --model`. Skippy resolves catalog names and Hugging Face
references, then reuses cached files or downloads what it needs. To open a
local GGUF, use `model = "./qwen.gguf"` or `model_path = "qwen.gguf"`.
Relative paths start in the directory containing the settings file. Choose
one source key per entry. Existing multi-model files must rename `path` to
`model_path` and keep `version = 1`.

Skippy loads every model before opening the listener. `GET /v1/models` lists
the IDs that clients can use in the request's `model` field. By default, the
ID is the catalog or Hub reference, or the filename stem for a local model.
Set `id` on an entry to give it an explicit name. All IDs must be unique.

Put common tuning under `[defaults]` and overrides under `[models.settings]`.
Environment variables and CLI tuning options apply to all entries. The list
defines the model sources, so use either `[model]` or `[[models]]` and
omit global source selectors such as `--model` when serving the list. Set the
listener with top-level `bind_addr` and the shared runtime under `[runtime]`.
Use `--print-effective-config` to inspect the settings and IDs before native
model load. Skippy can acquire the model files while preparing the report.

## How settings resolve

Settings resolve in this order:

1. Explicit command-line options.
2. `SKIPPY_SERVE_<OPTION_NAME>` environment variables.
3. Values in the serving settings file.
4. Admitted model/stage policy and built-in defaults.

Paths in a settings file are relative to that file. Paths supplied on the CLI
remain relative to the working directory. Unknown keys, wrong sections, invalid
values, and conflicting model sources are errors.

Environment variables use the CLI representation and the
`SKIPPY_SERVE_<OPTION_NAME>` form. For example,
`SKIPPY_SERVE_THREADS=8` sets `[execution].threads`; `--threads 4` overrides it.

## Configuration surfaces

| Surface | Best for | Example |
| --- | --- | --- |
| CLI | One run or a measured override | `--temperature 0.2` |
| Environment | Deployment-level process settings | `SKIPPY_SERVE_THREADS=8` |
| TOML | Versioned complete serving policy | `--settings serve.toml` |
| Admitted stage plan | Planner-owned split identity and tensor closure | `--config stage-0.json` |
